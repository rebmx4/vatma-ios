# Приватные уведомления соцсетей в ATMA — проект решения

> **Обновление 25.10.2026:** описанная ниже схема Web Push relay имеет платформенный блокер для ATMA: [Apple DTS](https://developer.apple.com/forums/thread/760767) подтверждает отсутствие Web Push в `WKWebView`. Это спецификация желаемого поведения и исследованной гипотезы, не технически подтверждённое решение. Реализация и выпуск остановлены на Gate A; см. [матрицу](../../research/2026-10-25-notification-provider-matrix.md).

Дата: 25 октября 2026. Статус: исследованная архитектура; совместимость ВК и Авито НЕ подтверждена.
Запрос владельца: придумать решение и подготовить план для GPT Sol. Этот документ не разрешает запуск сборки или публикацию.

## Что требуется

1. В настройках ярлыка и при его создании пользователь может включить уведомления о новых сообщениях.
2. На iPhone появляется «У вас новое сообщение ВК» / «У вас новое сообщение Авито», без текста, имени отправителя и превью.
3. На ярлыках внутри ATMA видны непрочитанные сообщения; на системной иконке ATMA — сумма: ВК 2 + Авито 4 = 6.
4. Доставка должна работать при свёрнутой ATMA, заблокированном экране и, в пределах возможностей iOS, при закрытом приложении.
5. Ни разработчик, ни сервер ATMA не получают доступ к открытому тексту переписки, паролям, cookie или токенам входа соцсетей.
6. Лайки, рекомендации, новости и реклама не должны превращаться в уведомления о сообщениях.
7. Вход в соцсеть остаётся внутри существующей вкладки ATMA. Не требуется оставлять компьютер пользователя включённым.

Конфиденциальность здесь означает отсутствие доступа сервера ATMA к содержимому. Зашифрованный пакет может проходить через сервер; ключ расшифровки остаётся на iPhone. Сама исходная соцсеть уже обрабатывает сообщения по своим правилам. Это не обещание сквозного шифрования переписки между собеседниками.

## Проверенные факты и неизвестное

| Вопрос | Состояние на дату документа |
|---|---|
| В текущей ATMA есть push-доставка? | Нет. Нет APNs-регистрации, Notification Service Extension и backend уведомлений. JS `notify()` показывает только toast. |
| Есть ли реализованный пример encrypted Web Push → APNs? | Да, `mastodon/webpush-apn-relay`, для Mastodon/Toot!, не для ВК/Авито. |
| Можно ли просто включить Web Push в WKWebView? | По ответу Apple DTS — нет; нативные APNs возможны. Service Workers при этом поддерживаются. |
| Примет ли ВК/Авито наш endpoint и ключи? | Не проверено на тестовых аккаунтах. Может мешать привязка к FCM/другому push-провайдеру. |
| Будут ли в событии вид сообщения и точное непрочитанное? | Не проверено. Уведомление, диалог и сообщение — разные единицы. |
| Можно ли отфильтровать любое нежелательное уведомление в NSE? | Для подавления remote alert нужно специальное разрешение Apple `com.apple.developer.usernotifications.filtering`. Оно не предоставляется автоматически. |
| Можно ли проверять сайты каждую минуту в фоне? | Нельзя обещать такой режим на iOS; фоновое выполнение назначает система. |

Вывод: транспорт технически обоснован, интеграция с конкретными соцсетями пока является гипотезой. Выпуск допустим только после проверки источника и настоящего iPhone.

## Выбранная архитектура

```text
Первичная настройка на iPhone:
ATMA создаёт отдельные Web Push ключи → передаёт сайту endpoint + публичный ключ + auth
Приватный ключ и auth остаются также в Keychain iPhone; сервер ATMA их не получает.

Доставка:
Сайт шифрует Web Push → relay ATMA пересылает ciphertext → Apple APNs
→ расширение ATMA на iPhone расшифровывает → извлекает только тип/счётчик/версию
→ общее уведомление + локальный счётчик → сумма на иконке ATMA
```

Это кандидат на реализацию, а не уже работающий универсальный браузерный Push API. Нужен небольшой совместимый адаптер подписки для каждого подтверждённого сайта. Он использует обычную авторизованную страницу пользователя; не выгружает сессию на сервер и не имитирует чужие APNs/FCM credentials.

Проверять отдельно: вызов `PushManager.subscribe`, получение существующей подписки, разрешение уведомлений, регистрацию на сервере сайта, отписку. Не подменять всем страницам `Notification.permission = granted`. Изменения ограничить проверенным origin и явным согласием владельца телефона. Для неизвестных сайтов API/интерфейс не должны обещать поддержку.

Не запускать произвольный service worker сайта в Notification Service Extension. Расшифрованный формат разбирает небольшой нативный адаптер из поставляемого кода. Если событие содержит только команду «сходи за перепиской», интеграция не проходит приватный режим без нового согласования.

## Условия допуска сайта

Результат проверки каждого источника — один из `unknown`, `blocked`, `prototype`, `verified` с конкретными доказательствами.

Для `verified` обязательны все условия:

- Сайт принимает нашу законную подписку, отправляет зашифрованные события после закрытия страницы; это не работа скрытого опроса.
- Подписка однозначно привязана к выбранному аккаунту и origin; есть проверенные признаки выхода и смены аккаунта.
- Есть подписка только на сообщения либо проверенное разрешение Apple на фильтрацию и различимый тип события.
- Есть достоверный счётчик непрочитанных **сообщений** либо эквивалентная полная модель событий с надёжной сверкой. Счётчик диалогов не переименовывать в сообщения.
- Проверены прочтение на другом устройстве, повторная доставка, пропуски, перестановка событий и восстановление связи.
- Не требуются серверные cookie, пароль, токен чтения переписки или расшифровка на сервере.
- Проверены допустимость используемого интерфейса сайта и отсутствие обхода CAPTCHA, ограничений доступа или чужих credentials.

Если один пункт не выполнен, нельзя объявлять полностью готовыми уведомления/цифру 6. Можно представить пользователю конкретный частичный вариант, но внедрять его вместо согласованного результата без согласования нельзя.

Первая проверка — ВК; Авито проходит такую же самостоятельную проверку. Удачный тест ВК не означает поддержку остальных соцсетей.

## Данные, ключи и границы доверия

| Где | Разрешённые данные | Запрещённые данные |
|---|---|---|
| Сайт / его WebView | Его собственная сессия, endpoint, публичный p256dh и auth подписки | Доступ к общему UI RPC ATMA, APNs token, чужим подпискам |
| Keychain iPhone | P-256 private key, auth, локальный ключ доступа к relay | Синхронизация секретов подписки через наш backend |
| App Group iPhone | Случайные ID подписок/эпох, связь с ярлыками, счётчики, версии, HMAC идентификаторов событий | Тексты, имена собеседников, вложения, история переписки |
| Relay ATMA | Случайный endpoint, APNs token, VAPID public key сайта, время/размер, ciphertext до TTL | Cookie, OAuth соцсети, p256dh private key, auth secret, открытый текст |
| APNs | Обычный заголовок ATMA, ciphertext или короткий ID зашифрованного объекта | Открытый текст и отправитель сообщения |

Relay технически видит IP соединений и метаданные доставки. Утверждение «вообще никаких данных не обрабатываем» неверно. Не хранить IP и полные URL подписок в access logs; логи только агрегированные коды ошибок/статусы. Сервисный APNs token не является полной анонимностью.

Ключи: CryptoKit, RFC 8291 `aes128gcm`; никаких собственных алгоритмов. `auth` — 16 случайных байт; отдельные ключи для origin/локальной сессии/подписки. Keychain `AfterFirstUnlockThisDeviceOnly` позволяет расшифровку при заблокированном экране после первого разблокирования; это осознанный компромисс для требуемого поведения. До первого разблокирования — только безопасный общий fallback, без выдуманного счётчика.

Удаление: отключение уведомлений немедленно выключает локальную подписку, исключает её из суммы и ставит отзыв endpoint в очередь. При сети relay возвращает 410 для отозванного endpoint и очищает его очередь. Приватный ключ удаляется. Отзыв сайта выполняется через его авторизованный интерфейс. Уже находящийся в APNs пакет нельзя гарантированно отозвать: допустим запоздалый общий fallback без содержимого; эту границу проверить и сообщить.

Выход из аккаунта/очистка cookie/смена учётной записи создают новую эпоху. Поздний пакет старой эпохи не изменяет новый счётчик. Невозможность надёжно обнаружить смену аккаунта — блокер провайдера, а не повод привязываться только к hostname.

Инкогнито: подписка запрещена, постоянные ключи не создаются. Закрытые PIN-страницы: не включать наружные уведомления автоматически; при переносе ярлыка предложить отдельно согласовать уведомления, по умолчанию отключить с отзывом. Не раскрывать скрытый ярлык переходом из уведомления мимо PIN.

## Счётчики и доставка

Единица учёта — уникальная связка провайдер + локальная сессия аккаунта, а не количество ярлыков. Два ярлыка одного аккаунта могут показывать одно число; в общей сумме оно учитывается один раз. Удаление одного дубликата не отзывает подписку другого.

Нативный SQLite ledger в App Group — единственный источник истины для счётчиков. UI получает снимок через существующий защищённый мост. App и NSE используют транзакции; JS localStorage хранит ярлыки, но не отдельную копию счётчика.

Число push-пакетов не равно числу непрочитанных. Не использовать `badge += 1`. Основной путь — абсолютный счётчик с серверной версией события; для другого формата требуется доказанный эквивалент и отдельный тест пропусков. Удаление баннера и открытие ATMA не означают прочтение сообщения. Обнулять только по подтверждению сайта.

APNs доставляет best effort. Отказ сети, Focus, отключённые пользователем alerts, перезапуск телефона, очереди APNs и чтение на другом устройстве могут задержать обновление. Точная цифра в любую миллисекунду при закрытом приложении не гарантируется. `verified` означает проверенную корректность после доставки/сверки, без превращения потерянного события в вечную ошибку.

Состояния ledger: `known(count, revision, observedAt)`, `stale(lastKnown, reason)`, `unknown`. UI явно отличает устаревшие данные. В строгом режиме системную числовую метку очищать при известной потере достоверности; не показывать частичную сумму как общий точный результат. iOS сама не гарантирует запуск кода для своевременного снятия старой метки — это документируемое ограничение.

Если сайт не присылает события прочтения/счётчики вне активной вкладки, требование точной суммы при закрытой ATMA не подтверждено. Не замещать его таймером `BGAppRefresh` или silent push.

NSE не вызывается для badge-only/silent пакета и может не работать при отключённых alerts. Основной пакет — alert с `mutable-content: 1`, исходным общим текстом «У вас уведомление» и без исходного `badge`. При успешной проверке на телефоне — «У вас новое сообщение ВК» и достоверная сумма. Текст сайта никогда не копировать в `UNNotificationContent`, attachments или логи.

Фильтрация на устройстве требует Apple entitlement. Даже с ним авария/тайм-аут расширения может показать исходный общий fallback. Поэтому предпочтительна подписка источника только на сообщения; не обещать абсолютного подавления всех нежелательных событий при сбое iOS.

## Relay

Минимальный стек: Python 3.12, SQLite, ASGI/uvicorn, httpx с HTTP/2 для APNs, cryptography для подписей ES256. Зависимости закрепить точными проверенными версиями при реализации. Отдельный каталог `notification-relay/`, никаких серверных ключей в iOS bundle.

HTTPS endpoint содержит случайный ID минимум 256 бит, не APNs token, email или ID ВК. Подписку ограничить VAPID key источника; проверять подпись, audience и срок. Регистрация/удаление доступны только установленному приложению с выданным ему секретом; ограничить скорость и объём, не делать открытый push-прокси.

Пакет APNs ограничен 4096 байт. Ciphertext после base64 может не поместиться: короткий пакет пересылается inline, большой — хранится зашифрованным до TTL и загружается расширением по авторизованному opaque ID. Максимум входящего ciphertext 64 KiB, TTL не больше 24 ч и срока источника. Усечение недопустимо. Тестировать отказ/тайм-аут загрузки и отсутствие plaintext fallback.

Relay не считает сообщения и не определяет тип уведомления: это невозможно надёжно сделать без расшифровки. Его порядковый номер доставки не является версией состояния соцсети. Повтор ciphertext можно отсеять по хешу в пределах TTL; содержательные дубликаты определяет телефон по аутентифицированному событию.

Постоянно работающий HTTPS сервер необходим. GitHub Actions — сборщик, не хостинг доставки. Использовать существующий сервер можно только после проверки ресурсов/доступа; новый платный сервис не покупать автоматически. Бесплатность браузера для пользователя не означает нулевые расходы эксплуатации.

## Альтернативы, если Web Push не подошёл

1. Официальная интеграция с источником, который выдаёт событие/число без содержимого. Формат `account.getCounters` в схеме VK существует, но права обычного стороннего приложения необходимо проверить; наличие метода не доказывает доступ.
2. Партнёрская поддержка у соцсети: сообщение без текста, адресованное нашей подписке. Для Авито публично обнаруженная API-интеграция мессенджера относится к профессиональным сценариям; универсальная доступность личным аккаунтам не подтверждена.
3. При отсутствии совместимого источника честно зафиксировать блокер и обсудить с владельцем ограниченный режим только при открытой ATMA. Не выпускать его как выполненное исходное требование.

ИИ/DeepSeek, серверный браузер с cookie пользователя, чтение чужих уведомлений других iOS-приложений, непрерывный фоновый WebView и маскировка под VoIP/audio исключены. Safari PWA на домашнем экране iOS не заменяет ярлык внутри ATMA и не создаёт общий badge ATMA.

## Основания

- [Web Push → APNs relay для Mastodon](https://github.com/mastodon/webpush-apn-relay): подтверждает идею транспорта, не совместимость ВК; старый пример нельзя копировать как готовый безопасный сервер.
- [RFC 8291](https://datatracker.ietf.org/doc/html/rfc8291), [RFC 8292](https://datatracker.ietf.org/doc/html/rfc8292): шифрование и привязка отправителя.
- [Apple DTS о WKWebView](https://developer.apple.com/forums/thread/760767): Web Push и нативные APNs — разные пути.
- [Apple: изменение уведомления на устройстве](https://developer.apple.com/documentation/usernotifications/modifying-content-in-newly-delivered-notifications): NSE, условия запуска, ограничение времени и fallback.
- [Apple: право фильтрации](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.filtering): отдельная заявка и разрешение Apple.
- [Apple: фоновые стратегии](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app): опрос каждую минуту не гарантируется.
- [VK account schema](https://github.com/VKCOM/vk-api-schema/blob/master/account/methods.json), [Avito Messenger](https://avito.akamaized.net/business/tools/messenger): направления проверки альтернатив, не подтверждение доступных прав ATMA.

Рекомендуемая модель для реализации: GPT-6.1 Sol, уровень high. Причина: нужны согласованные изменения криптографии, нативного iOS-кода, сервера и состояния аккаунтов.
