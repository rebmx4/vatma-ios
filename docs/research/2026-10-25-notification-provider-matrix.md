Дата проверки: 25 октября 2026. Только публичные страницы и исходники; владелец вошёл в ВК и Дзен на iPhone в старой сборке 13, но авторизованные сессии и реальные сообщения исследованию недоступны. ## Наблюдения из первых рук

1. `https://vk.com/` перенаправляет неавторизованный запрос на `https://m.vk.com/`. В публичном `first_wave` скрипте есть обращения к `serviceWorker`, но в загруженном без входа наборе нет вызова `pushManager.subscribe` или конфигурации ключей. Сайт может загружать нужный код только после входа; отсутствие вызова в гостевом наборе ничего не доказывает о подписке авторизованного пользователя.
2. Официальная [схема ВК `account.getCounters`](https://github.com/VKCOM/vk-api-schema/blob/master/account/methods.json) принимает **пользовательский токен**. [Объект ответа](https://github.com/VKCOM/vk-api-schema/blob/master/account/objects.json) содержит `messages` с описанием «New messages number». Это направление для альтернативы с отдельным согласием на API-доступ, а не подтверждение, что счётчик приходит с push или доступен обычной вкладке ATMA без токена.
3. Открытый клиентский скрипт Авито `bootstrap-desktop` содержит `firebase-messaging`, `pushManager.subscribe`, `applicationServerKey` и `Notification.requestPermission`. Публичный [service worker Авито](https://www.avito.ru/firebase-messaging-sw.js) принимает событие `push`, читает его JSON и показывает `notification` из полезной нагрузки. В самом worker нет явного поля `unread`; содержимое настоящего события и число непрочитанных всё равно неизвестны. Не копировать оригинальный текст уведомления в ATMA.
4. Поскольку Авито использует Firebase Messaging, успешный вызов `pushManager.subscribe` в Safari ещё не доказывает, что Firebase примет endpoint ATMA или доставит пакет в `WKWebView`. Не подменять Firebase token или чужой APNs topic. Отдельный сетевой тест endpoint имел бы смысл лишь после появления поддерживаемого провайдером и платформой канала.
5. [Apple DTS](https://developer.apple.com/forums/thread/760767) прямо говорит, что Web Push не работает в приложениях с `WKWebView`, хотя Service Workers работают. Нативные APNs работают только когда само приложение имеет источник событий. Поэтому предложенный relay для Web Push сайта нельзя считать реализуемой доставкой в текущем ATMA, даже если сайт пользуется Firebase Messaging в Safari/Chrome. Авторизованный тест может уточнить поведение конкретного сайта, но не устраняет ограничение платформы.
6. [Авито для бизнеса](https://avito.akamaized.net/business/tools/messenger) предлагает Messenger API для CRM при наличии подходящего тарифа/подписки и ключей из кабинета «Для профессионалов». Это отдельная интеграция, не автоматический доступ для любого обычного пользователя ATMA. Неизвестно, доступен ли API владельцу тестового аккаунта и можно ли получать только счётчик без передачи содержимого сообщения на сервер.
7. Официальная схема ВК также описывает [`account.registerDevice`](https://github.com/VKCOM/vk-api-schema/blob/master/account/methods.json): пользовательский токен, токен устройства, ID устройства, настройки push и sandbox. Это конкретная зацепка для обращения к ВК, но схема не говорит, принимает ли ВК APNs-токен стороннего приложения `ru.atma.browser` и может ли отправлять только факт нового личного сообщения без текста/имени. По [документации Apple](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns) токен уникален для пары устройство—приложение; [APNs topic](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns) обычно равен bundle ID и требует соответствующей авторизации отправителя. Передать токен ATMA ВК и считать доставку рабочей нельзя.
8. По [документации Apple](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) и [WWDC25](https://developer.apple.com/videos/play/wwdc2025/235/) Web Push поддерживается Safari и установленными на экран «Домой» веб-приложениями; это не подтверждение поддержки внутри `WKWebView`. Установленная сборка 13, по проверенному исходному коммиту, допускает только фоновое аудио и отвергает `aps-environment` при проверке подписи. Для native APNs ATMA нужен новый подписанный бинарник, но до источника событий такая сборка ничего не доставит.
9. Фильтрация зашифрованного произвольного push уже на iPhone тоже не готовое решение: обычная Notification Service Extension меняет видимое уведомление, а [подавление уведомлений](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.filtering) требует отдельного entitlement. Чтобы обещать «только сообщения», источник должен надёжно отделять их до видимого APNs либо нужно отдельно подтверждённое право на фильтрацию.

## Что нужно для Gate A

Для альтернативного источника сначала нужен официально поддерживаемый контракт каждого провайдера: разрешение пользователя, доставка в собственный APNs topic ATMA после закрытия приложения, доступ к сигналу именно личного сообщения и точному числу непрочитанных, синхронизация прочтения/выхода без доступа сервера ATMA к тексту или пользовательским токенам. Для ВК следующий предметный вопрос — разрешён ли `account.registerDevice` для стороннего bundle с таким ограниченным payload. Для Авито — доступно ли событие без содержимого и без бизнес-тарифа обычному пользователю. Дзен пока отдельно не проверен. Если контракт существует, проверить на устройстве только метаданные: origin, код результата, признак события сообщения, единицу и версию счётчика, факт синхронизации прочтения/выхода. Никаких токенов, cookie, полного endpoint, имён, текста или вложений не экспортировать.

Сценарий после нахождения контракта: два сообщения в одном чате, ещё одно в другом, несообщение, прочтение на другом устройстве, выход и смена аккаунта. Реальный тест требует iPhone и диагностической сборки либо доступного авторизованного браузера. Сейчас инструмент компьютерного браузера сообщил `No browser is available`; пользователь получил инструкцию войти внутри ATMA на iPhone. Один только вход в существующую сборку не даёт фоновых уведомлений и не снимает ограничение `WKWebView`. Гостевые страницы не устанавливают ни `blocked`, ни `verified` для провайдерского API.

На компьютере подготовлен [probe с белым списком полей](../../tools/notification-probe/README.md). Его synthetic-тест проверяет, что в отчёт не попадают текст сообщения, cookie, токен и полный адрес push endpoint. Он сам по себе не исследует личную переписку.

## Решение на этой стадии

Gate A остаётся открытым. Исходная архитектура Web Push relay теперь имеет подтверждённый платформенный блокер: Apple не доставляет Web Push в `WKWebView`. Запускать сервер APNs, включать переключатели уведомлений и обещать счётчик `2+4=6` до нахождения и проверки другого разрешённого источника нельзя. Диагностическая iOS-сборка для одной лишь попытки Web Push подписки не разрешит этот блокер и сейчас не нужна. Для точной реализации закрытого приложения нужен иной провайдерский контракт или изменение требований владельцем; никаких дополнительных сборок до этого не запускать.
